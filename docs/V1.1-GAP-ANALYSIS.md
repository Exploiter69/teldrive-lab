# TelDrive Lab v1.1 Gap Analysis

## Purpose

This document is the architecture checkpoint between the completed `v1.0.0` release and v1.1 implementation.

v1.0 established the trustworthy control-plane foundation. v1.1 is not a feature-collection exercise. Its purpose is to improve operational visibility, recovery, evidence, and safe use of capabilities that already exist in the Lab.

## Architectural decision

The v1.1 sequence is:

```text
A  Control Center operational depth
            ↓
B  Recovery / restore workflows
            ↓
C  Observability + evidence
            ↓
D  Storage intelligence integration
            ↓
E  CAS / dedup safety investigation
```

This order is deliberate. Visibility and recovery must become stronger before advisory storage intelligence is connected to consequential workflows. CAS/dedup is last because it has the highest destructive-risk surface.

## Global invariants

Every v1.1 change must preserve:

- TelDrive as production storage authority.
- No direct TelDrive PostgreSQL writes.
- No authorization minted by planner, worker, UI, advisory layer, or AI.
- Consequential mutation only through the controlled executor boundary.
- Verification after consequential execution.
- Durable Lab-owned evidence/audit.
- No automatic destructive production operation.
- Bounded traversal, indexing, queries, pagination, and reports.
- Zero-cost runtime; no paid service or API dependency.
- No mandatory local or cloud LLM.
- Optional integrations remain optional.
- Production data is never a disposable test fixture.
- Existing v1.0 behavior remains regression-safe.

## Stage A — Control Center operational depth

### Gap

The current Control Center already provides live catalog, job, transfer, media, health, audit, configuration, and search views. The gap is operational depth: stale/recoverable state, discovery/index freshness, richer deterministic summaries, and explicit read-model contracts.

### Prerequisites

1. Run the full v1.0 test/gate matrix and record the baseline.
2. Confirm existing R5 Control Center tests and host gate pass.
3. Map JobStore states and lease semantics.
4. Map catalog verification/index semantics.
5. Map audit event fields and lifecycle transitions.
6. Define bounded response limits and deterministic ordering before adding endpoints.

### Acceptance

- Versioned read-model schemas.
- Explicit freshness/unknown semantics.
- Active/failed/recoverable/stale job visibility.
- Lease/recovery visibility.
- Search/index health.
- Storage/media/audit summaries where data already exists.
- GET-only, loopback-only boundary preserved.
- Unit, HTTP, host, and full regression tests pass.

## Stage B — Recovery / restore

### Gap

Durable execution already survives leases and process boundaries. The next layer is making recovery decisions explicit and understandable rather than leaving recovery as low-level job-store behavior.

### Prerequisites

1. Stage A complete.
2. Disposable fixtures for failure/recovery scenarios.
3. Deterministic failure taxonomy.
4. Stable recovery-plan identity/digest.
5. Existing authorization/executor boundary identified for each operation.
6. Restore verification path available.

### Acceptance

```text
failure → evidence → classification → recovery plan → explicit authorization
→ controlled execution → verification → audit
```

Retry/resume/restore must be bounded, idempotency-aware, worker-fenced where applicable, and unable to bypass production protection.

## Stage C — Observability / evidence

### Gap

The Lab has audit and durable job state. v1.1 should make lifecycle correlation and failure analysis easier without creating a competing evidence system.

### Prerequisites

1. Stage B complete.
2. Audit schema reviewed.
3. Job/plan/execution/verification lifecycle mapped.
4. Secret/path exposure review defined.

### Acceptance

- Consequential transitions have sufficient durable evidence.
- Job/plan/event correlation is deterministic.
- Failure/retry/recovery history survives restart.
- Reports are bounded and deterministic.
- Sensitive data is not unnecessarily exposed.

## Stage D — Storage intelligence integration

### Gap

Deterministic storage/cache intelligence and analytics exist but should become useful operational advice without becoming automatic mutation.

### Prerequisites

1. Stage C complete.
2. Existing intelligence code audited against current product contract.
3. Finding semantics deterministic.
4. Plan identity/digest stable.
5. Controlled executor and verification path identified.

### Acceptance

```text
finding → plan → human review → explicit authorization → executor → verify → audit
```

Candidates may be reported for archive, backup, organization, or cleanup, but `finding → DELETE` is prohibited.

## Stage E — CAS / dedup investigation

### Gap

CAS and report-only dedup remain experimental. Before any promotion, identity, provenance, collision, incomplete-hash, rollback, and source-authority semantics must be proven.

### Prerequisites

1. Stages A–D complete.
2. Content identity specification.
3. Provenance model.
4. Collision handling.
5. Rollback/recovery model.
6. Cross-source semantics.

### Acceptance

At minimum:

- report-only dedup remains safe;
- incomplete hashes cannot become false identities;
- collisions are detected and retained as evidence;
- provenance survives planning;
- rollback assumptions are tested;
- production remains protected;
- no automatic production deduplication is introduced by implication.

## What is not a v1.1 gap

The following are explicit non-goals, not missing features:

- Whisper / speech-to-text
- Ollama or mandatory local LLM runtime
- cloud AI APIs
- autonomous AI mutation or authorization
- automatic production eviction
- automatic production deduplication
- unbounded remote workers

## Definition of done

A v1.1 stage is not complete merely because code exists. It must reach:

```text
PRIMITIVE
→ IMPLEMENTED
→ INTEGRATED
→ OPERATIONAL
→ END-TO-END VERIFIED
→ DOCUMENTED
→ COMPLETE
```

For release, the exact candidate must also pass clean-install, full regression, complete gate matrix, production-boundary validation, and documentation/release-contract review.
