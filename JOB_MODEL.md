# TelDrive Lab — Job Model

**Status:** Architecture contract  
**Scope:** Durable asynchronous work execution inside TelDrive Lab  
**Authority:** TelDrive Lab control plane only; TelDrive and Telegram remain storage authorities

## 1. Purpose

The Job Model defines how TelDrive Lab represents, persists, executes, retries, verifies, recovers, and audits work that may outlive a CLI process, worker process, network connection, or machine session.

A job is a **durable execution contract**, not merely an in-memory task.

The central invariant is:

> A job is not complete merely because an operation returned successfully. It is complete only after all required verification has succeeded and the result has been recorded.

The Job Engine must therefore survive process restarts, worker loss, temporary network failure, Telegram/API throttling, partial transfers, and interrupted verification without losing the authoritative intent or silently repeating unsafe work.

---

## 2. Architectural Position

The Job Engine sits between the deterministic planning/policy layer and execution backends.

```text
User / CLI / Scheduler
        │
        ▼
     Planner
        │
        ▼
  Policy + Authorization
        │
        ▼
   Durable Job Engine
        │
        ├── Transfer Manager
        ├── Archive Manager
        ├── Indexer
        ├── Integrity Verifier
        ├── Backup/Snapshot Manager
        └── Other controlled executors
        │
        ▼
     Verification
        │
        ▼
       Audit
```

The Job Engine does **not** become a storage authority. It records intended and observed work against the systems defined by the Production Boundary and Safety Contract.

---

## 3. Job Types

The initial canonical job types are:

- `UPLOAD` — transfer data into an approved destination.
- `DOWNLOAD` — transfer data from an approved source.
- `ARCHIVE` — execute an approved archive workflow.
- `VERIFY` — verify content, metadata, or transfer integrity.
- `BACKUP` — create or validate an approved backup.
- `SNAPSHOT` — create or validate an approved snapshot/manifest.
- `ORGANIZE` — perform deterministic, explicitly authorized organization work.
- `CLEANUP` — perform explicitly authorized lifecycle cleanup.
- `INDEX` — discover and reconcile metadata into the Lab catalog.
- `RESTORE` — restore from an approved backup/snapshot after explicit authorization.

Additional job types require an architectural decision and must not be introduced as arbitrary executor-specific strings.

---

## 4. Job Identity

Every job has a globally unique `job_id` generated by the Lab.

A job may additionally carry an idempotency key where the operation has an external side effect. Idempotency identity must be deterministic enough to detect safe re-submission without treating unrelated operations as duplicates.

Jobs must never rely on process-local memory for identity or lifecycle state.

---

## 5. Canonical Job Fields

The initial persistent model contains at least:

| Field | Meaning |
|---|---|
| `job_id` | Stable unique job identifier |
| `type` | Canonical job type |
| `priority` | Scheduling priority |
| `state` | Current lifecycle state |
| `created` | Job creation timestamp |
| `started` | Most recent execution start timestamp |
| `updated` | Last state/progress update timestamp |
| `completed` | Completion timestamp when terminal |
| `attempts` | Number of execution attempts |
| `max_attempts` | Retry ceiling |
| `retry_at` | Earliest time a retry may run |
| `source` | Source descriptor/reference |
| `destination` | Destination descriptor/reference |
| `path` | Logical path or bounded target identifier |
| `size` | Expected or observed size when known |
| `checksum` | Expected/observed integrity value when applicable |
| `progress` | Informational execution progress |
| `error_code` | Stable classified failure code |
| `error_message` | Human-readable diagnostic |
| `worker_id` | Current worker lease owner |
| `lease_until` | Lease expiration timestamp |
| `parent_job_id` | Optional parent workflow job |

Implementations may add fields, but must preserve the semantics of these canonical fields.

Sensitive credentials, session tokens, raw authorization headers, or secret material must never be stored in job fields.

---

## 6. Lifecycle States

The canonical states are:

- `QUEUED`
- `RUNNING`
- `PAUSED`
- `VERIFYING`
- `COMPLETED`
- `FAILED`
- `CANCELLED`

Normal execution is:

```text
QUEUED → RUNNING → VERIFYING → COMPLETED
```

Failure handling may return a retryable job to `QUEUED` after the retry policy determines that another attempt is permitted.

Cancellation is cooperative and must leave enough persisted information for the system to determine whether partial work requires reconciliation or verification.

A terminal state must never be inferred merely from worker process exit.

---

## 7. State Transition Rules

State transitions are explicit and persisted.

### Allowed baseline transitions

```text
QUEUED      → RUNNING
QUEUED      → CANCELLED
RUNNING     → PAUSED
RUNNING     → VERIFYING
RUNNING     → QUEUED
RUNNING     → FAILED
RUNNING     → CANCELLED
PAUSED      → QUEUED
PAUSED      → CANCELLED
VERIFYING   → COMPLETED
VERIFYING   → QUEUED
VERIFYING   → FAILED
CANCELLED  → [terminal]
COMPLETED  → [terminal]
FAILED     → [terminal unless an explicit retry/requeue policy creates a new attempt]
```

Implementations may refine these transitions, but arbitrary state mutation is forbidden.

Every transition must record sufficient audit information to explain what happened and why.

---

## 8. Persistence and Restart Survival

The durable job state lives in the Lab runtime data area and is independent from the TelDrive production database.

The Job Engine must persist:

- job identity;
- requested operation;
- scope and source/destination references;
- authorization relationship where required;
- current state;
- attempt count;
- retry schedule;
- worker lease;
- verification requirements;
- failure classification;
- parent/child relationships;
- relevant progress/checkpoint information;
- audit linkage.

After a process restart, the Job Engine must reconstruct pending work from persisted state rather than assuming that in-memory queues still exist.

A crash must not erase a job that was accepted by the durable queue.

---

## 9. Worker Leasing

Workers execute jobs under a renewable lease.

A lease contains at least:

- `worker_id`;
- `lease_until`;
- last update/heartbeat information.

The lease prevents two workers from normally executing the same job simultaneously while still allowing recovery from a dead worker.

When a lease expires:

1. the job is considered abandoned, not automatically successful;
2. the engine reconciles the last known execution state;
3. partial external work is treated as potentially present;
4. the job may be safely re-queued only according to its idempotency/reconciliation rules;
5. the recovery is audited.

A worker must not extend a lease after losing ownership.

---

## 10. Retry Model

Retries are classified rather than unconditional.

### Retry classes

**Transient**

Temporary network failures, service interruptions, temporary I/O errors, or other failures expected to resolve without changing the requested operation.

**Rate-limited**

Telegram/API throttling or equivalent provider limits. Retry timing must respect the provider's indicated delay and Lab safety limits.

**Permanent**

Invalid input, missing source, forbidden destination, authorization failure, unsupported operation, or another condition that will not be repaired by repetition.

**Integrity**

A transfer or result was produced but failed verification. The engine must reconcile the observed state before deciding whether another attempt is safe.

### Retry requirements

Retries use:

- bounded exponential backoff;
- jitter where appropriate;
- maximum attempts;
- classified errors;
- idempotency/reconciliation checks;
- explicit audit records.

There is no infinite retry loop.

Repeated identical failure signatures should eventually stop rather than consuming resources indefinitely.

---

## 11. Idempotency

Every executor must define what happens if the same job is attempted more than once.

The preferred behavior is one of:

1. detect that the requested result already exists and verify it;
2. safely resume from a persisted checkpoint;
3. reconcile partial state before continuing;
4. refuse repetition when safety cannot be established.

A retry must never blindly duplicate a potentially destructive or externally visible operation.

Idempotency is especially important for uploads, downloads, restores, organization, cleanup, and operations interrupted after external side effects but before local state was persisted.

---

## 12. Progress Semantics

`progress` is informational.

It may represent bytes transferred, items processed, stages completed, or another executor-specific metric, but it is never proof of correctness.

For example:

```text
progress = 100%
state    = VERIFYING
```

means the transfer stage reports completion but verification is still outstanding.

Only successful verification can establish completion where verification is required by the operation contract.

---

## 13. Verification Contract

Jobs that mutate or transfer data must define their verification requirement before execution.

Typical verification includes:

- source/destination existence;
- expected size;
- checksum comparison;
- readable content;
- expected metadata;
- manifest reconciliation;
- destination visibility through the supported interface.

If verification fails, the job must not be marked `COMPLETED`.

Depending on the failure, the job may:

- retry after reconciliation;
- enter `FAILED`;
- require human intervention;
- create a follow-up verification/recovery job.

---

## 14. Parent and Child Jobs

Complex workflows may be represented as a parent job with durable child jobs.

Example:

```text
ARCHIVE
├── HASH
├── DUPLICATE_CHECK
├── UPLOAD
├── VERIFY
└── INDEX
```

Parent jobs describe the workflow intent. Child jobs perform bounded stages.

A parent cannot report success while a required child is incomplete or failed.

Child jobs inherit safety constraints from the parent but retain independent durable identity and auditability.

Child jobs must not expand the authorized scope beyond the parent's approved scope.

---

## 15. Priority

The initial priority classes are:

1. `CRITICAL`
2. `HIGH`
3. `NORMAL`
4. `LOW`
5. `BACKGROUND`

Priority influences scheduling only.

**Priority never bypasses:**

- policy checks;
- authorization;
- rate limits;
- resource limits;
- production boundaries;
- verification;
- cancellation;
- safety gates.

A `CRITICAL` job is not permitted to become an unsafe job merely because it is urgent.

---

## 16. Offline-First Behavior

Network-dependent jobs must distinguish between:

- local work that can continue offline;
- work waiting for network access;
- work blocked by provider availability;
- work that must be reconciled after reconnection.

Temporary loss of network connectivity should normally produce a retryable condition rather than corrupting the job or falsely marking it failed permanently.

Network recovery must not cause an uncontrolled burst of queued Telegram/API traffic.

---

## 17. Startup Recovery

On Job Engine startup, recovery must inspect persisted state for at least:

- expired worker leases;
- `RUNNING` jobs with no valid lease;
- incomplete verification;
- abandoned transfers;
- stale retry schedules;
- interrupted child workflows;
- inconsistent terminal/verification state.

Recovery is reconciliation, not blind replay.

The recovery procedure must prefer conservative classification when external state cannot be established.

---

## 18. Cancellation

Cancellation must be persisted.

Workers should stop at safe checkpoints rather than abruptly abandoning external operations whenever possible.

After cancellation:

- the job must not resume automatically unless explicitly re-authorized/requeued;
- partial effects must be reconciled where relevant;
- verification may still be required to understand the final state;
- the cancellation must be audited.

Cancellation cannot be used to bypass verification or hide partial work.

---

## 19. Safety and Authorization Boundary

The Job Engine does not grant authority.

Authorization is established before execution for operations requiring it, and the persisted job must remain bound to the approved scope.

A job cannot:

- broaden its path scope;
- change destination class;
- convert a read-only operation into a write operation;
- turn a non-destructive plan into deletion;
- modify protected production configuration;
- alter DNS/network exposure;
- replace TelDrive or its database;
- silently migrate or re-upload existing data.

If a worker discovers that execution would exceed its authorized scope, it must stop and report the condition.

---

## 20. Destructive Jobs

`CLEANUP`, `ORGANIZE`, `RESTORE`, and any future operation that may overwrite, delete, move, rename, or otherwise create irreversible effects require the Safety Contract lifecycle:

```text
PLAN
  ↓
DRY-RUN
  ↓
EXPLICIT AUTHORIZATION
  ↓
EXECUTE
  ↓
VERIFY
  ↓
AUDIT
```

The job record must retain enough information to prove which approved operation it represents.

A queued destructive job is not itself permission to execute.

---

## 21. Failure Semantics

Failure information must be structured enough to support diagnosis and retry decisions.

At minimum, failures should distinguish:

- policy rejection;
- authorization rejection;
- missing source;
- destination unavailable;
- network failure;
- provider rate limit;
- timeout;
- local resource exhaustion;
- integrity mismatch;
- worker crash/lease expiry;
- cancellation;
- unsupported operation;
- unknown/internal failure.

Unknown failures default to conservative handling rather than aggressive retry or destructive recovery.

---

## 22. Resource Awareness

The Job Engine must operate within the host's resource envelope.

Scheduling must account for:

- available RAM;
- CPU pressure;
- disk/cache capacity;
- active transfer count;
- provider rate limits;
- concurrent verification cost.

The engine must prefer bounded concurrency over maximum throughput.

A backlog is acceptable. Resource exhaustion that destabilizes the host is not.

---

## 23. Auditability

The following events should be auditable:

- job created;
- authorization attached;
- queued;
- started;
- worker leased;
- progress/checkpoint changed when materially relevant;
- paused/resumed;
- retry scheduled;
- retry attempted;
- verification started;
- verification passed/failed;
- completed;
- failed;
- cancelled;
- lease expired/recovered;
- child created/completed/failed;
- recovery/reconciliation performed.

Audit records must never contain secrets.

---

## 24. Catalog Relationship

The Job Model and Data Model have different responsibilities.

**Job Model:** what work is requested, executing, retrying, verifying, or completed.

**Data Model:** what the Lab knows about files and storage observations.

A job may reference catalog records, but a catalog record must not be treated as proof that an operation completed.

After successful execution and verification, the job may trigger catalog reconciliation/indexing.

---

## 25. CLI Relationship

The initial CLI exposes job state through commands such as:

```text
`td jobs`
`td status`
`td upload`
`td download`
`td archive`
`td verify`
`td backup`
`td snapshot`
`td restore`
```

CLI commands should submit durable jobs rather than embedding long-running execution logic directly in the command process.

The CLI must be able to inspect a job after the originating process exits.

---

## 26. Scheduling Principles

The initial scheduler should be deliberately simple:

1. recover abandoned work;
2. identify runnable queued jobs;
3. enforce policy and resource constraints;
4. select by priority and age;
5. acquire a worker lease;
6. execute one bounded unit of work;
7. persist the resulting state;
8. verify when required;
9. release the lease;
10. audit the outcome.

Fairness and starvation prevention should be considered when implementing priority queues, but must not introduce uncontrolled concurrency.

---

## 27. Initial Implementation Boundary

The first implementation should provide:

- SQLite-backed durable jobs;
- schema versioning;
- canonical job types and states;
- explicit transition validation;
- durable creation and queueing;
- worker leases;
- retry scheduling;
- bounded exponential backoff with jitter;
- cooperative cancellation;
- parent/child relationships;
- idempotency/reconciliation hooks;
- verification state;
- structured failure codes;
- startup recovery;
- audit events;
- deterministic tests for crashes, retries, lease expiry, cancellation, and verification failure.

Do not begin with distributed workers, a remote queue, Kubernetes, Redis, Kafka, or another operationally heavy dependency. The initial Job Engine is local-first and should remain resource-efficient.

---

## 28. Required Safety Tests

Before the Job Engine is considered complete, tests must prove at least:

1. a queued job survives process restart;
2. a running job with an expired lease is recovered safely;
3. an already-completed external result is detected instead of blindly duplicated;
4. transient failures retry within bounded limits;
5. rate-limited failures respect retry timing;
6. permanent failures do not retry indefinitely;
7. integrity failures never produce `COMPLETED`;
8. cancellation persists and prevents unintended resumption;
9. a parent cannot complete with an incomplete required child;
10. priority cannot bypass policy or authorization;
11. a job cannot exceed its approved scope;
12. unknown failure defaults to conservative handling;
13. audit events are produced for important transitions;
14. secrets are absent from persisted job/audit data;
15. resource limits prevent unbounded worker concurrency.

---

## 29. Architectural Invariants

The Job Engine must preserve these invariants:

1. **Durability:** accepted work survives process failure.
2. **No false success:** required verification must pass before completion.
3. **Bounded retries:** no infinite automatic retry.
4. **Idempotency:** retries cannot blindly duplicate unsafe effects.
5. **Lease safety:** abandoned workers can be recovered without assuming success.
6. **Scope integrity:** jobs cannot expand their authorized scope.
7. **Authorization separation:** queue presence is not authorization.
8. **Auditability:** important state transitions are explainable.
9. **Cancellation:** cancellation is respected and persisted.
10. **Resource safety:** scheduling remains bounded and host-aware.
11. **Production isolation:** the Lab cannot silently replace or mutate protected TelDrive infrastructure.
12. **Storage authority:** the Job Engine never becomes the source of truth for stored content.
13. **Conservative recovery:** uncertainty results in reconciliation or human intervention, not unsafe assumptions.

---

## 30. Completion Definition

A Job Engine phase is complete only when:

- the schema is implemented and versioned;
- lifecycle transitions are validated;
- persistence survives restart;
- leases and recovery are tested;
- retry classes and backoff are tested;
- idempotency/reconciliation behavior is defined for each executor;
- verification gates completion;
- cancellation is tested;
- parent/child semantics are tested;
- audit records are generated;
- resource limits are enforced;
- production-boundary and safety tests pass;
- documentation matches the implementation.

The governing principle is:

> **A job is durable intent plus bounded execution plus verified outcome.**

The worker may disappear. The process may disappear. The network may disappear. The job contract and its evidence must remain.
